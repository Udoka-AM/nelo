This page is kept honest rather than flattering. The distinction between *a test exists* and *a test has run* is the one that matters, and for most of this project's life it cut the wrong way. It no longer does — but the parts that are still only written say so.

**566 TypeScript tests, plus the Rust and LiteSVM suites below, all green, all on every push.** Everything but the LiteSVM suite runs with no phone and no validator — which is the whole reason the arithmetic was pulled out of the app and the program in the first place.

The LiteSVM tests were the long-standing gap. They went unexecuted for weeks because no machine that had the repo had the Solana toolchain — `release.anza.xyz` is unreachable from the development environment. The first run scored **39 of 40**, and [the one failure was worth more than the 39 passes](#things-that-went-wrong-and-were-caught).

## What CI runs

`.github/workflows/ci.yml`, on every push and every pull request:

| Job | What | Cold | Warm |
|---|---|---|---|
| **TypeScript** | 566 tests, then four typechecks | ~21s | ~21s |
| **Rust (host)** | `cargo fmt`, clippy, 19 unit tests, 7 golden-vector tests | not yet timed | ~34s |
| **Anchor** | the 45 LiteSVM tests | ~14m | ~2m once the build cache is warm |

The Rust job is deliberately separate from the Anchor one: the curve carries no Anchor types precisely so it can be checked without a validator, and it answers in seconds instead of waiting on a toolchain install. The Anchor job pins from `Anchor.toml`'s own `solana_version` and `anchor_version`, and is week 4's graded deliverable — *clone → install → `anchor test` green* — run on a machine that starts with nothing.

<Note>
**The typecheck job exists because of a pattern, not a principle.** Every defect that has reached `main` was a TypeScript error found by a person reading code. [See below](#what-that-gap-already-cost).

Each check is negative-tested rather than trusted: removing the `ScrollView` import gives `TS2304`, renaming an export in `@nelo/pay` gives `TS2724`, and a malformed function makes `cargo fmt --check` exit 1. A job that cannot fail is not worth adding.
</Note>

## What still has never run

<Warning>
**The merchant app has never rendered.** A development client **does not embed the JS bundle**; it loads it from Metro at runtime, so compiling the native side proves nothing about the screens. No merchant screen has been drawn and no component has mounted. It typechecks clean under `strict`, which is a real result and not the same result.

The payer app **has** now rendered on a handset, so the shared halves — Hermes, the bundler, the native module boundary — are no longer in question. The till is.
</Warning>

<Warning>
**StrongBox still has not run, and now for a different reason.** `@nelo/attest` compiles, loads and answers on a real handset — but the handset that ran it **has no secure element**, so the two deepest checks never executed: keygen with attestation, and a hardware signature verifying against the device key.

That second one is the one to worry about. Android Keystore returns DER with an S that may sit in the upper half of the curve order; a high-S signature verifies on the phone and is **rejected on chain**. `derToRawSignature` normalises it, and is tested against `@noble/curves` — a library agreeing with a library. Whether real Keystore output survives it is still unknown, and it is a defect that would only ever appear on hardware, in a demo.
</Warning>

<Note>
**What the handset did answer.** Four checks passed on a real device: BigInt and DataView under Hermes, P-256 sign and verify under Hermes, and the 202-byte round-trip. None of those could be settled off-device — Hermes handles both BigInt and `DataView` differently from Node.

It also produced the finding: **no StrongBox**, on ordinary mid-range hardware. `packages/attest`'s capability record now writes that answer down in a fixed form on every device the probe runs on, because how common that is across the launch markets is an input the reserve model currently guesses at.
</Note>

<Warning>
**The Privy calls have never executed.** The flow machine around them has 29 tests, but `useLoginWithSMS` and `useEmbeddedSolanaWallet` need an app ID and a device. The call sites were typechecked against the published `@privy-io/expo` declarations, which catches shape errors and nothing about behaviour.
</Warning>

**Paused 24 Sep, no Android device available. Resuming within three days.** Recorded here
rather than remembered, because the next session starts cold.

### Answered, and not worth repeating

| | |
|---|---|

| Payer probe, mid-range handset | 4 of 5 — no secure element, which is the finding `packages/attest`'s capability record now writes down |

The first row retires the risk that mattered most. Android Keystore returns DER with an S
that may sit in the upper half of the curve order — it verifies on the phone and is
**rejected on chain**. `derToRawSignature` was only ever checked against `@noble/curves`, a
library agreeing with a library. It is now checked against real Keystore output.

### The one test still open

**A payment that registers on the till.** Money arrives, the balance reads it back on reload,
and the terminal does not flip to Paid.

Three defects were found and fixed off-device — a malformed `getSignaturesForAddress` (the
commitment was a loose third parameter), a `catch {}` that hid it, and polling that stopped
after 120 seconds while the screen still said the code was live. **None of that is confirmed
on a handset.** The last attempt was against a bundle whose provenance is unverified: the
dev client could not reach Metro, and it is not established whether the fix was in the
bundle that finally loaded.

So the fix is proven by nine tests and unproven in the field.

<Note>
**First three things when a device is available.**

1. `cd ~/nelo && git pull && git log --oneline -1` — confirm the working tree carries the fix
   before reading anything into a result.
2. Take one payment through Solflare's home scanner. The charge screen now prints the
   **reference** and the full `solana:` request under the QR in development builds.
3. Read the status line, which now discriminates: `Waiting for payment…` means the RPC is
   answering and no transaction names the reference; `Cannot reach the network` means it is
   not; red text means detection worked and validation refused.

Then look the reference up on an explorer. No transaction naming it means the wallet never
attached it and the terminal is right to wait — which moves the bug upstream, into the
request rather than the detector.
</Note>

<Note>
**The offline path, once a device is back.** Nothing below has run on a handset.

1. **Rebuild both development clients.** `expo-camera` is a new native module in both apps,
   and the payer app also gained Mobile Wallet Adapter, SQLite and SecureStore:
   `pnpm --filter @nelo/merchant build:dev` and `pnpm --filter @nelo/payer build:dev`, then
   install both APKs.
2. **Start the relay on the Mac and put its tunnel URL and token in `apps/merchant/.env`.**
   See [Relay](/operations/relay). It pays for settlement, so the merchant needs no SOL and
   signs nothing, however they signed up.
3. **Open the till online once.** It syncs every vault for devnet USDC. The payer's vault must
   exist on chain before the till goes offline, or the scan says the payer is not on the list.
4. **Set up the payer phone online first:** Connect wallet (it needs devnet SOL and devnet
   USDC), enter an amount, **Open my offline wallet**. One wallet approval opens the vault
   and locks the USDC. Then open the till online once more so it syncs the new vault.
5. **Both phones in airplane mode.** Till: enter an amount, **Charge**. Payer: **Pay a
   merchant**, scan the till's code, **Pay**. Till: **Customer has no signal? Scan their
   code**, scan the payer's code, **Hand over the goods**. Scan the same payer code again: it
   must be refused.
6. **Reconnect and tap the orange bar.** No wallet prompt: the relay submits. The bar reports
   each voucher paid, waiting to confirm, or held. The relay's terminal shows nothing on success;
   `relay-ledger.json` records every submission.
</Note>

## What that gap already cost

Not hypothetical. While adding the balance display:

```ts
// apps/merchant/App.tsx
import { awaitPayment, type PaymentOutcome } from "@nelo/pay";
```

`packages/pay/src/index.ts` **never re-exported either of them.** `awaitPayment` would have been `undefined` at runtime — the till would have crashed the moment a merchant pressed **Charge**.

No test caught it, and at the time none could have: the app had never been bundled and there was no CI. It was found by reading imports while adding an unrelated feature.

Then it happened again. While wiring onboarding:

```tsx
// apps/merchant/App.tsx — the day-book screen
<ScrollView contentContainerStyle={styles.bookBody}>
```

`ScrollView` was **never imported.** Tapping **Today** would have thrown. Found the same way — by eye, adding something else.

Then a third, when `tsc` was pointed at the apps for the first time: they could not typecheck the packages **at all**. The config error stopped the check before it reached a line of app code.

<Note>
All three are TypeScript errors. All three were found by a person reading code. None needed an emulator, a handset or an Android toolchain to catch.

That is why the typecheck job exists, and why it is four separate invocations rather than a hopeful one. Reading is not a method; it is what is left when there is nothing to run — and now there is.
</Note>

The gap that remains is narrower but real: a typecheck proves the types, not the render. Nothing in either app has drawn a screen.

## How the tests are written

<AccordionGroup>
  <Accordion title="Negative tests before positive ones" icon="ban">
    Everywhere in the vault. The **first test in `vault.rs`** is the one that must fail: a *valid* P-256 signature over *different* bytes has to be rejected.

    Get the precompile offsets wrong and every positive test below still passes while the program verifies nothing at all. A test that passes because nothing was checked is worse than no test.
  </Accordion>

  <Accordion title="Golden vectors across the language boundary" icon="file-code">
    `packages/voucher/vectors/voucher-v1.json` is generated by the Rust side — the chain is authoritative — and asserted by both. TypeScript also verifies signatures that Rust produced, so the check covers the crypto and not only the byte layout.
  </Accordion>

  <Accordion title="Properties, not just examples" icon="function">
    The curve is tested for sublinearity **at every doubling across six orders of magnitude**, not at one convenient point. `isqrt` is brute-forced against its floor property including at `u128::MAX`. The money splits are checked to add back exactly, at every amount in a list chosen to include the awkward ones.
  </Accordion>

  <Accordion title="Read the balance, not the field" icon="eye">
    The LiteSVM tests read the **SPL token account**, deliberately not the vault's `balance` field. The two must agree, and reading the field to check the field proves nothing.
  </Accordion>
</AccordionGroup>

## Things that went wrong, and were caught

Kept because they are more informative than the passes:

| What | Caught by |
|---|---|
| Two cap tests asserted a cap that was unreachable at the inputs chosen | The tests failing on first run |
| A vacuous assertion — `sq <= u128::MAX`, always true | `cargo clippy` |
| FX legs in the payout that cancelled to nothing, leaving the transaction unbalanced | Working the double-entry through by hand |
| A test asserting custody empties after a full payout, when the platform fee stays behind | The test failing |
| Two test objects built by spreading a class instance — the methods live on the prototype, so they never implemented the interface | `tsc --strict` |
| A misread Poisson table asserting a quantile of 3 where `P(X≤2)` already cleared the confidence | The test failing |
| A test that refused the right thing for the wrong reason, proving nothing | `anchor test`, the first time it ran |

Most were caught by a tool or a test rather than by reading. The one that was not — the FX legs — was a design error, and the ledger's own balance rule would have rejected it at runtime anyway.

### The one worth reading twice

The first-ever `anchor test` run scored 39 of 40. The failure was `only_the_risk_authority_can_publish_reputation`, and it was not the program.

The test helper passed the same keypair twice — once as fee payer, once as the instruction's signer. A message dedupes its account keys, so it required **one** signature while the transaction builder was handed **two**, and failed with `NotEnoughSigners` *before the program was entered*.

So the test got an error, `is_err()` was satisfied, and the property it names — *reputation you can set yourself is not reputation* — had **never been checked**. The authority constraint was there and correct, but correct-by-inspection is not proven.

<Note>
**Failing was the good outcome.** Had the assertion been on `is_err()` alone, it would be green today and still empty. Its sibling test passes only because an impostor keypair happens to differ from the payer, so it never hit the trap at all.

That is the argument for asserting on the *reason* rather than the fact of a refusal, and it is why every check added to CI was negative-tested before being trusted.
</Note>

## The gate rehearsal

The week-3 gate, *two phones in airplane mode, a sale completes, both reconnect, it settles, and the replayed voucher is refused*, run against a real validator with the product's own code rather than a test's. The payer's vault is opened with `@nelo/redeem`'s builders, the voucher issued by `@nelo/issue`, the tills sync with `@nelo/enrol`, decide with `@nelo/till` and keep what they take in its SQLite store, and they settle with `@nelo/queue` through the relayer from `services/relay`, over HTTP. While the phones are offline, `fetch` is switched off in the process, so anything that reached for the network would fail the run.

```bash
pnpm rehearse                                      # RPC from ~/.config/nelo/relay.env
pnpm rehearse --rpc http://127.0.0.1:8899          # a local validator
pnpm rehearse --keypair ~/.config/solana/id.json   # who pays for the run
```

It checks, in order:

1. **Offline sale.** The payer's phone reads till A's code and signs; till A checks it with no network and takes it. The same code shown again is refused.
2. **Settle.** Till A reconnects and settles through the relayer. The merchant is paid exactly the sale, holds no SOL, and the vault pays out exactly that.
3. **Replay.** Asked again, the relayer answers with the transaction that already landed and sends nothing. Sent straight to the program, bypassing the relayer, it is refused by the replay window (`SequenceTooOld` once the window's base has moved past it, `SequenceAlreadyRedeemed` inside it).
4. **Double spend.** A tampered phone signs a second voucher at the same sequence for till B. Till B takes it offline, as it must. On reconnect it is not paid, the relayer reports the conflict, and the vault freezes on chain.
5. **Slash.** The relayer's sweep moves the vault's whole stake into the reserve.
6. **After the freeze.** The payer's phone will not sign once it has synced. A voucher signed before the freeze is still taken by a till, with the frozen-vault warning shown, and the chain pays it from the locked collateral, as the program intends.

Each run makes fresh wallets and its own 6-decimal test mint, costs about 0.15 SOL on devnet, and sends what is left back to the funder. It refuses to run against mainnet.

**Where it has run: a local `solana-test-validator` (Agave 4.2.2) with the program built from this commit, twice, both passing. Not yet on devnet**: the development environment cannot reach it. Two things are stood in for: the secure element (a software P-256 key) and the two phones (one process).

<Note>
**Slashing on devnet depends on who controls the stake mint.** The risk config is created once per cluster, and its stake mint is whatever the first run gave it. On a fresh validator the rehearsal creates both and makes the funder the mint authority. On devnet it reads the stake mint's authority and, unless it is the funder, stakes nothing and reports the slash step as skipped rather than passed. If the devnet risk config was created by the week-1 `devnet.rs` run, its stake mint and its update authority were a throwaway key from that run, and neither can be used again.
</Note>

## The devnet gate

The week-1 trust model has been run end to end on devnet **against the Trust Stake build**: vault funded, `RiskConfig` initialised, voucher redeemed with the device signature verified by the secp256r1 precompile **on a real validator**, double-spend refused, signature-over-other-bytes refused.

That distinction matters. The gate had passed before, but against a build that predated the Trust Stake. This run is the first time `RiskConfig` has existed on a real validator and the first time `redeem_voucher` has been exercised on chain with its new account struct — exactly the kind of change LiteSVM can accept and a validator reject.

```bash
cargo test -p nelo_vault --test devnet -- --ignored --nocapture
```

`#[ignore]` so it never runs in the default suite. It creates its own 6-decimal mint, so a run is self-contained, and it costs devnet SOL.

<Note>
It uses a **software P-256 key** in place of StrongBox. That is deliberate: it isolates *"does the chain do what we think"* from *"does the handset do what we think"*. The second question is still open.
</Note>
