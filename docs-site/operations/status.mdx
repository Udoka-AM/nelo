Nelo is a hackathon project built against a four-week plan. This page is the honest ledger of where it actually is.

<Note>
Three states are kept apart, because conflating them is how a demo ends up claiming something untrue:

- **Proven** — a test that has actually executed, or a run on devnet
- **Written** — code exists and compiles, but has never run
- **Declared stub** — deliberately not real, and labelled as such at every call site
</Note>

## The four things that block the most

<Steps>
  <Step title="Find a handset with a secure element">
    The payer probe has now run on real hardware and scored **4 of 5**. Hermes, the codec, P-256 and the native module boundary are all answered. The fifth is the finding: that handset has **no StrongBox**, so keygen-with-attestation and the hardware signature never executed — and the low-S normalisation of Android Keystore's own DER is still proven only against a library.

    Until a device with a secure element runs the probe, the offline path cannot be demonstrated. A Pixel 3 or later, a recent Samsung flagship, or a Solana Seeker will do it.
  </Step>
  <Step title="Render the merchant till">
    A development client loads its JS from Metro, so compiling the native side proves nothing about screens. The payer app bundling settles that half for both, but no till screen has been drawn and no state transition has run outside a test.
  </Step>
  <Step title="Get a Privy app ID">
    Onboarding's done-when is *setup completed without ever seeing a key*, and it cannot be demonstrated without one. The flow's rules are tested; the SDK calls are typechecked and unexecuted. A build with no app ID runs and simply does not offer the phone route.
  </Step>
  <Step title="Get paj.cash's staging key and answers">
    The cash-out is built against paj.cash's published API. It needs their staging key to run for real, and their answers on whose account runs the session, whether staging takes devnet USDC, and their failure states.
  </Step>
</Steps>

## Decisions waiting on a person

<AccordionGroup>
  <Accordion title="Which launch currency, or which oracle" icon="money-bill-transfer">
    Pyth publishes **no NGN feed** — 39 FX pairs, and the naira is not among them. Of the markets the plan names, Manila (PHP) is covered; Lagos is not.

    Either pick a covered launch currency, or source NGN from Switchboard or a commercial feed. Hermes also requires an API key for prices. Until one is settled, the till runs a configured rate and says so on screen.
  </Accordion>

  <Accordion title="The reserve line, and the premium claim" icon="calculator">
    **The reserve line is settled.** [The reserve model](/economics/reserve-model) found the 0.20% line did not cover expected loss — 28.07 bps implied — and the rate charged is now 29 bps, which takes the net take rate to 0.61%.

    **The premium claim is not.** Reserve relief funds a premium of ~1.001×, not the illustrative 1.5×. That is a change to how the deck describes it, not to the architecture, and it should be settled before submission.
  </Accordion>

  <Accordion title="k and the hard cap, together" icon="sliders">
    The curve raises required reserve below ~$250 of staked value, and the $500 hard cap needs $81,000 of stake to bind. Neither parameter can be fixed without the other.

    Both are `RiskConfig` updates rather than redeploys.
  </Accordion>

  <Accordion title="Whether to widen the conflict proof" icon="scale-unbalanced">
    `report_conflict` only freezes on two vouchers at the **same** sequence. Successive sequences with inconsistent `remaining_after` do not trigger it, and that residual is what the insurance line prices.

    Accepting that pair as proof would shorten the window a compromised device keeps trading in. It changes the fraud model, so it is flagged rather than taken.
  </Accordion>
</AccordionGroup>

## What is deliberately not built

Named rather than discovered, because a named stub reads as confidence and a discovered one reads as spin:

- **Paying out of the reserve.** `slash` moves a frozen vault's whole stake into the reserve, an account owned by the risk-config PDA, so no key can move it. Nothing pays out of it yet. Deciding who is compensated, by how much and on whose say-so is a commercial and legal decision, and the program should not invent the answer.
- **Cash-outs in the double-entry journal.** The journal was modelled on Nelo holding merchants' money. Cash-outs are non-custodial, so only Nelo's fee belongs in it, and that posting is not written.
- **Embedded-wallet recovery.** `needs-recovery` is detected and reported; `useRecoverEmbeddedWallet` is not wired, so the retry on that screen will not clear it. It arises when a wallet has to be reconstructed on a new device, which is exactly the case a merchant who changes phones hits — so it is a gap with a date on it, not a permanent omission.
- **Moving a vault to a new phone.** The program has no instruction to enrol a new device key on an existing vault, so a payer who loses the phone's key needs a new wallet.
- **The payer chooses their own floor limit.** `initialize_vault` accepts any `floor_limit` up to the platform hard cap, which makes staking pointless for anyone who asks for the cap. The payer app does not expose the knob and asks for $50, but the program should bound it.
- **NFC.** QR first, as planned; NFC has not been started.
- **Holes in the replay window.** The window advances only over contiguous redeemed sequences, so a voucher that is never redeemed leaves a hole the base cannot pass. After 127 more vouchers the vault can no longer pay offline. Fixing it is a program change, not yet designed.
- **Relay hosting.** The relayer runs on the founder's Mac behind a quick tunnel for the demo. A quick tunnel's URL changes when it restarts; production needs a fixed host.
- **Payer onboarding without SOL.** The payer app still enrols and deposits through the payer's own wallet, which needs SOL for fees and rent. The relayer cannot sponsor those instructions as they stand, because they require the vault owner's signature.
